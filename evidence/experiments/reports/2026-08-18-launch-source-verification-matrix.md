# PayLock 48-Hour Launch Source Verification Matrix

**Status:** Private, read-only launch-verification workpaper begun 2026-08-18. This record is not public copy, does not alter any protected repository, and does not itself establish production readiness.

## Objective and decision rule

The purpose is to compare the owner-approved operational lifecycle to the observable code and retained evidence before the planned launch window closes. Every row receives one classification:

| Classification | Meaning for launch wording |
| --- | --- |
| **Implemented** | A reviewed source path directly enforces the behavior, with a traceable location and, where available, retained test evidence. |
| **Configurable** | The source supports the behavior only when a defined contract, signal mapping, policy, or deployment configuration supplies it. Public wording must say it is configurable rather than universally present. |
| **Integration-dependent** | The behavior belongs to a provider Adapter, client component, or reference-platform contract that is not established as a completed reusable production integration. It cannot be stated as completed product behavior. |
| **Absent / contradicted** | The reviewed source does not establish the behavior or materially conflicts with it. It must be removed from launch claims or corrected under separate owner approval. |

No text may be classified as **Implemented** merely because it appears in a README, test plan, or demo route. Conversely, no source observation changes the owner-approved boundary without an explicit owner decision.

## Invariant protocol boundary

PayLock does not collect, query, verify, infer, attest, govern, or control payment information, payment status, funds, custody, or settlement. The launch verification concerns delivery governance of a digital product or service after a provider declares it ready.

The invariants under review are: a bound request identity; required participant agreement where imposed by the integration; controlled one-time delivery or unlock semantics; no partial success after an interrupted atomic transition; traceable outcome proof; and no silent conversion of a payment-related field into a proof condition.

## Evidence standard

Each completed row must record a precise source path, a relevant function/route or immutable artifact, the observed result, and a claim boundary. Test-only signals generated with the same privileged credential as Core are useful for behavior checks but do not prove independent provider authenticity. Public launch material must link only to evidence that is independently reproducible and appropriately redacted.

## Phase 2 finding: invariant proof versus integration semantics

**H0 and H1 remain strong reviewed Core invariants.** The material issue is not their derivation or single-winner storage; it is the semantic source of the current provider-side signal and the unimplemented Adapter boundary around it. `platform.js` currently contains payment receipt inputs and optional payment webhooks, and the reviewed mapping artefact maps payment events. This must be treated as a launch-copy and integration-layer remediation question, not as a defect in the H0/H1 proof construction.

## External receiver verification (bounded)

On 2026-08-18, the configured GitHub repository webhook was verified through its signed `ping` and one owner-authorized redelivery. GitHub reported HTTP `202` on both records and showed the endpoint configured with JSON content, TLS verification, an obscured secret, and the `release` event only. The receiver source verifies the SHA-256 HMAC before it returns the non-release `event_not_in_test_scope` disposition. This supports endpoint reachability and the shared-secret signing path only; it does not execute, infer, or establish a `release.published` provider-ready candidate, an Adapter mapping, or a PayLock Core transition.
